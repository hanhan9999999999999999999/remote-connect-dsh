# phone-bridge —— 手机 ↔ 电脑 的 DSH 通道

这个目录才是现在真正在跑的手机通道（根目录 `server.py` / `guardian.py` 那套是上游 bigeye 的原版结构，
见 `../手机电脑互联-文件地图.md`）。整条链路零第三方依赖，只用 Node 内置模块 + Windows 自带的 PowerShell。

## 功能一览（先看这里）

手机浏览器（或配套 APK）连上电脑这一端之后，能做这些事：

| 功能 | 怎么用 | 一句话说明 |
|---|---|---|
| **直播看世界** | 会话上方「直播」条 → 开播 | 手机一张一张把画面送过来，AI 在会话里直接点评；每眼 2–1800 秒、边长 480–2560、质量 20–98 都能调 |
| **拍一张给他看** | 相机按钮 / 直播条「拍一张」 | 立刻拍一张发给 AI，照片以「我」的身份进会话，点开能看全 |
| **他看到了没有** | 直播条右上角缩略图 | 发出即「已送到」，AI 真答上话了才变「他看到了」；点开就是刚发出去的那一帧 |
| **会话与历史** | 顶部「历史」 | 读电脑上的 DSH 会话存档，接续、切换、新建都在手机上完成 |
| **语音** | 按住说话 / 自动朗读 | 手机说话转文字；回复可用 Edge 或本机 GPU 语音读出来（可换音色、语速） |
| **待办 / 提醒 / 偏好** | 设置里 | 与电脑共用一份，手机改了电脑就变 |
| **全链路诊断** | 设置 →「全链路诊断」 | 摄像头、服务、隧道、守护逐项报告，卡在哪一环一眼看到 |
| **APK 安装包** | 电脑上打开 `/apk` | 装好之后相机走原生预览，比浏览器稳；装完打开一次即生效 |

三步上手：① 电脑上把桥接跑起来（见下一节）→ ② 手机连同一个 WiFi 打开 `http://<电脑IP>:8899`，或用 APK →
③ 设置 →「全链路诊断」确认摄像头与隧道都是绿的，再点开播。

> 直播这条线每一处改动、踩过的坑、自测方式，都按版本记在下面的 **§15 直播看世界**；
> 判断「为什么没截到帧」，先看 **§15.60 / §15.62** 和「全链路诊断」那三行。


```
手机浏览器(同一 WiFi) ──HTTP/SSE──> server.mjs :8899 ──stdio/文件──> DSH 会话存档 ~/.dsh/sessions
                                        │
                                        ├─ tts.mjs      TTS 路由（Edge / 肥鱼 CosyVoice3 / 系统音色）
                                        ├─ tools/feiyu-tts-service.py  本机 GPU 语音服务 :8898（可选）
                                        ├─ sessions.mjs 读会话存档（zstd 帧增量解析）
                                        ├─ todos.mjs / prefs.mjs / reminders.mjs  待办、偏好、提醒
                                        └─ link.mjs     局域网/隧道地址探测
```

## 一、启动与守护

| 入口 | 说明 |
|---|---|
| `dsh-phone-guard.vbs`（启动文件夹快捷方式） | 每秒级不管事，**每 60 秒** `GET /api/health`；活着就什么都不做 |
| `ensure-running.ps1` | 桥接没在服务时：按端口占用者（8899）杀旧进程 → 选 node → 后台拉起 → 最多等 30 秒 health |
| `ensure-seekmemory.ps1` | SeekMemory 内核（`127.0.0.1:8791`）没在服务时拉起；已有进程先给 45 秒再决定杀 |
| `..\启动肥鱼语音.bat`（根目录） | 可选：本机 GPU 语音服务 `127.0.0.1:8898`。`start`（默认）/`console`/`stop`/`status`；模型常驻显存，首次加载约 9 秒 |

VBS 里两条脚本都是同步调用的：桥接守护失败不影响 SeekMemory 守护，反之亦然。

**公网隧道也有自己的看门狗。** `link.mjs` 每 30 秒（`PHONE_TUNNEL_WATCH_MS`）探一次公网 `/api/health`；
隧道进程退出、或连续两次探活失败，就重建；重建失败按 30s → 60s → 120s → 240s → 300s 退避重试，直到成功。

> 旧版这里是个死区：看门狗只认 `state.running`，而隧道进程一退出 `state` 就被 `clearState()` 清空，
> 之后每 120 秒的 tick 第一行就 `return` —— **隧道断了就再也不重连**，只能重启桥接进程。
> 现在改用 `desired`（「应该有一条隧道」的意图）判断，`/api/link/state` 多返回 `desired` 与 `retryIn`
> （下次重试倒计时秒数）；断开和重建都会写进 `runtime/bridge.log`，形如
> `tunnel 公网通道断开：自建隧道进程退出（code 255）（看门狗会每 30 秒重试）` /
> `tunnel 公网通道重建：旧地址 -> 新地址`。
> 自测方式：`Get-CimInstance Win32_Process -Filter "Name='ssh.exe'"` 找到带 `18899` 的那条杀掉，
> 40 秒内 `/api/link/state` 应当自己变回 `running: true`，公网 `/dsh/api/health` 回到 200。

手起也行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File phone-bridge\ensure-running.ps1
```

**改这两个 .ps1 必须保住 UTF-8 BOM。** Windows PowerShell 5.1 没有 BOM 时会按 GBK 解码，
中文注释能让脚本直接解析失败（`Expressions are only allowed as the first element of a pipeline`）。
`write`/`edit` 工具会剥掉 BOM，改完补一句：

```bash
node -e "const f=require('fs'),p='phone-bridge/ensure-running.ps1',s=f.readFileSync(p,'utf8');if(s.charCodeAt(0)!==0xFEFF)f.writeFileSync(p,'\uFEFF'+s)"
```

## 二、鉴权

- `runtime/state.json` 里的 `token`（手机端存在 `localStorage['dsh.tk']`）
- 请求头 `x-phone-token: <token>`，或查询串 `?t=<token>`
- 首次配对用 `pairCode`（同一个文件里），配对成功后手机拿到 token，之后都带 token 走
- 页面加载时会把 `?t=` 存进 `localStorage` 并立刻从地址栏抹掉；`/health` 不返回任何地址/配对码，
  所以局域网里没令牌的人拿不到钥匙。`/api/token/reset` 可一键换钥匙（设置页有按钮）。

## 四、会话存档读取（这套里最容易踩的坑）

DSH 把每个会话写成 `~/.dsh/sessions/<转义过的 cwd>/<session-id>/session.v4.jsonl.zstd`，
是**多帧 zstd 首尾相接**，每轮追加一帧或几帧。本机现状：90+ 个会话、约 120 MB，最大单个 26 MB。

`sessions.mjs` 的做法：

1. `scanFrames()` 只读帧头拿边界，`readRange()` 只读文件尾部新增的那段；
2. 每个文件维护一个累加器 `{mtimeMs, size, byteEnd, previews, …}`，`updateOne()` 命中
   `mtimeMs + size` 未变就直接返回缓存，变了才从 `byteEnd` 往后解新帧；
3. `byteEnd` 只推进到**完整帧末尾**，半帧留到下一轮再读（边写边读不会裂）；
4. 落盘索引 `runtime/session-index.json`（v2，约 0.7 MB）：只存元信息 + 每会话最近 240 条预览，
   进程重启后直接复用，不用重解压；
5. 预览带上限（内存 400 条 / 单条 900 字），避免「点开一次就涨内存」。

只出现在工具轮次里的回答（没有正文、只有工具调用）会折成 `⏺ 工具名` 兜底，
否则这类会话在手机上标题是「(无标题)」、点进去一片空白。

性能（同一台机器，改前 → 改后）：

| 操作 | 改前 | 改后 |
|---|---|---|
| `GET /api/sessions`（冷） | 14.09 s | 5 ms |
| `GET /api/sessions`（热） | 0.15 s | 5 ms |
| 最大会话正文（3717 条） | 826 ms | 1.8 ms |
| 冷建索引（一次性） | — | 4.1 s，之后 4 ms |

## 五、历史会话导出（本轮新增）

`POST /api/session/export` + 历史抽屉里的「导出」按钮：

```bash
curl -X POST http://127.0.0.1:8899/api/session/export \
  -H "x-phone-token: $TOKEN" -H 'content-type: application/json' \
  -d '{"ids":["session-xxxx"],"limit":200}'
```

- `ids` 最多 30 个；`limit` 为 0（默认）表示整份，>0 表示只导出最近 N 条；
- 走 `fullTranscript()`：重解压整份存档（26 MB ≈ 1.9 s），所以在按钮上先弹确认、再显示「正在导出」；
- 输出一个合并的 `workspace/exports/history-<时间戳>.md`，每会话一节，正文不裁剪；
- 历史抽屉里**没勾选**时导出最近 30 个会话，会先 `confirm` 问一声。

## 六、落盘层：原子写、备份、坏档隔离（`store.mjs`）

所有用户数据（`state.json`、`messages*.jsonl`、`todos.json`、`reminders.json`、
`life-prefs.json`、`memory.jsonl`、`session-index.json`）都走 `store.mjs`。原因是这一类
事故在这台机器上真的发生过：

- 直接 `writeFileSync` 全量覆盖，进程被杀或断电会在文件中间留半截；
- 半截 JSON 下一次 `JSON.parse` 失败，各模块的 `catch` 一律当作空数据；
- 紧接着第一次改动又 `save()` 一遍，把残留也覆盖掉 —— 数据永久消失
  （`messages.jsonl` 被写成 0 字节、历史全丢，就是这条路）。

| 函数 | 做什么 |
|---|---|
| `writeAtomic(file, data)` | 写 `.tmp-<pid>-<时间>` → `fsync` → `rename` 覆盖；同分区内原子。写前把旧文件存成 `file.bak`（只留一版） |
| `readJson(file, fallback)` | 主档坏了先 `rename` 成 `file.corrupt-<时间戳>`（只留最近 5 个），再回退 `file.bak`，最后才用默认值 |
| `readJsonLines(file)` | 逐行 JSON，坏行跳过并返回 `{items, bad, bytes}` —— 一行半截不再毁掉整份历史 |

`GET /api/diag` 的 `stores` 字段是这套的体检报告：每个文件的 `size` / `mtimeMs` /
`bak` / `corrupt`。`corrupt > 0` 说明刚有坏档被隔离，旁边的 `.bak` 就是上一版。

`POST /api/backup` 还原后会把 `todos` / `reminders` / `memory` / `messages` 从磁盘重新载入
（`reload()`），不用重启桥接才生效。

```bash

# 或显式指定：npm run test:e2e -- "http://127.0.0.1:8899/?t=$TOKEN"
```

## 九、踩过的坑（改之前先看这里）

1. **node 不是 PATH 里那个**：真正在跑的是
   `%USERPROFILE%\AppData\Local\openai\codex\runtimes\cua_node\<hash>\bin\node.exe`。
   守护脚本按「cua_node 最新 → dsh 自带 node → PATH」顺序找。
2. **进程命令行里没有目录**：桥接命令行是 `"...\node.exe" server.mjs`，所以别用
   `-match 'phone-bridge'` 找进程，永远匹配不到；按 8899 端口的占用者杀才准。
3. **`$args` 是 PowerShell 自动变量**，别拿它接 `Start-Process -ArgumentList`，用 `$argList`。
4. **UTF-8 BOM**：见第一节。
5. **`NUL` 这种设备名文件**：目录里出现过一个叫 `NUL` 的文件（内容是 localhost.run 的 host key），
   PowerShell 的 `-LiteralPath`/`Remove-Item` 会把它当空设备，删不掉也读不到；用 msys 的
   `mv NUL runtime/known_hosts.localhost.run` 才行。
6. **历史抽屉「空白」不是前端 bug**：是后端 14 秒才返回 + 前端 1.5 秒就超时渲染的判断，
   修的是后端缓存（第四节）。
7. **`new URL(import.meta.url).pathname` 会把目录名的空格编码成 `%20`**：`memory.mjs` 和
   `sync-profile.mjs` 因此把 `memory.jsonl` / `profile-sync.json` 写进了
   `D:\document\Remote%20Connect%20DSH\` 这个影子目录 —— 记忆功能表面在跑、实际数据全在别处，
   `/api/backup` 也扫不到它。2026-10-31 改成 `fileURLToPath(import.meta.url)`，数据迁回
   `runtime/` 并删掉影子树。新模块一律用 `fileURLToPath`。
8. **还原备份不 reload 等于没还原**：`todos` / `reminders` / `memory` 都是模块初始化时读一次盘，
   旧代码只把内存里的消息数组复制了一遍，还原完要重启桥接才生效（见第六节）。
9. **`bridge.pid` 曾经有两本账**：`mcp-phone.mjs` 只记「自己拉起的那一个」，守护脚本拉起的桥接
   它不认，于是 `phone_stop` 杀完自己的 pid 就报失败、端口还在监听。现在 pid 由 `server.mjs`
   在 listen 回调里写（以真正监听者为准），`phone_stop` 再按 `netstat -ano` 找 8899 的占用者一起杀。
10. **在 msys bash 里 `spawn(detached:true)` 拉守护脚本会被带走**：`node -e "spawn(...,{detached:true})"`
   看着返回了，进程却没活下来（日志里连 STARTED 都没有）。改 `spawnSync` 同步等它跑完
   （约 2 秒），能直接拿到 `status` 和输出。
11. **看门狗用「当前是否在跑」判断，等于没有看门狗**：隧道进程一死，`state.running` 就是 false、
    `state.url` 是 null，于是 tick 里的 `if (!state.running || !state.url) return;` 每 30 秒
    忠实地什么都不做 —— 隧道断了就永远连不回来，只能重启桥接。凡是「要它自己恢复」的东西，
    判据必须是**意图**（`desired`），不是**现状**（`running`）。同一个坑的第二面：`start()`
    原来只在成功分支里 `startWatch()`，首次建隧道失败就再也不会重试。
12. **回归用例别写死关键词**：e2e 的「搜索并仅看命中」原来固定搜 `备份`，一旦当前会话
    被清空或换了内容，命中数必然 0 → 回归永远红。现在从最后一条消息里挑一个「前面各行
    都没出现」的片段当关键词，行数不足时只验控件行为、不算失败。

## 十、剪贴板（2026-11-06）

设置页 →「剪贴板」可以在手机和电脑之间搬一段文字：读电脑当前复制的内容，或者把手机里
贴进来的文字写进电脑剪贴板。实现只有 `clipboard.mjs` 一个文件，走本机 PowerShell 的
`Get-Clipboard` / `Set-Clipboard`，不装依赖。

- 需要令牌（和聊天同级），上限 64KB，所有请求串行化，避免两个请求同时抢剪贴板。
- **编码坑**：中文不能直接塞进 PowerShell 的 stdin（会被按 GBK 解码成乱码），
  统一写临时文件 + `UTF8Encoding($false)` 读写，绕开控制台代码页。
- 电脑锁屏时读取会失败，接口返回可读的错误，不会把桥接卡住。
- 实测往返中文/emoji 正常，单次约 1.6–2.0 s（PowerShell 冷启动占大头）。

## 十一、会话草稿（2026-11-06）

草稿按会话分开存在手机本地：`dsh.draft:<sessionId>`。切历史会话、切任务/相处模式、开新会话
时，先把输入框里的字存到旧会话，再换 `histId`，最后恢复新会话的草稿；恢复期间用
`switchingDraft` 屏蔽 input 事件，避免「刚恢复的字被旧草稿覆盖」（这是之前退回全局一份的原因）。

- 旧版本的全局 `dsh.draft` 会在第一次打开时迁到当前会话，然后删掉，不会丢。
- 发出去、清空历史会删掉当前草稿；清空历史还会把输入框一起清掉。
- 删掉/切走一个会话不会删它的草稿键；同一会话下次打开还在（上限 8000 字）。
- 回归新增「每个会话的草稿互不串台」：A 会话输入 → 切 B 输入 → 切回 A，逐项比对
  localStorage 与输入框，不碰真实发送。

搜索框的「仅看命中」也补了一个重建后的补丁：命中长消息会自动点「展开全文」并
`renderAll()`，以前重建后过滤类丢失，看起来像整屏都显示；现在 `renderAll()` 末尾会
调用 `window.__reapplyOnlyHits()` 把过滤补回去。

## 十二、语音识别（2026-11-02 换代）

原来走 Windows 自带的 `System.Speech`（`tools/asr_once.ps1`），离线免费但中文很差：
「大肥鱼你好今天天气不错」会被识成「83因为今天真是不错」。

现在优先走 **whisper.cpp**，通过 ffmpeg 自带的 `whisper` 滤镜（本机 ffmpeg 编译时带了
`--enable-whisper`），失败才回退到 System.Speech。

### 模型

| 文件 | 大小 | 说明 |
|---|---|---|
| `models/ggml-base.bin` | 148 MB | 主用 |
| `models/ggml-silero.bin` | 0.9 MB | VAD，用来掐掉静音段 |

**为什么不用 small**：实测 small 在低信噪比中文上会「编句子」——
测试音频被它翻成「你不要再說了,我會把你帶走的」，而原话是「你不想要我去找你吗」。
幻听比认错字危险得多，所以留 base。

下载源用 `hf-mirror.com`（HuggingFace 直连超时）。

### 三道后处理

1. **VAD**（`vad_model`，阈值 0.5）—— 不给静音段开口的机会
2. **同音纠正表** `FIXUPS` —— `大肥云/大肥與/大肥羽/大肥俞…` 一律改回「大肥鱼」
3. **幻觉清理** —— whisper 会把噪声翻成 `(字幕:J Chong)` 这种字幕署名，正则删掉

### 实测

| 音频 | 结果 | 耗时 |
|---|---|---|
| 3.4 秒 | 大肥鱼你好,今天要做什么?你不想要我去找你吗? | 1.4 s |
| 6.5 秒 | 大肥鱼你好,今天要做什么?你去哪了? | 3.0 s |

比原来的 System.Speech（2.8 秒、准确率约三成）又快又准。

### 维护备忘

- 模型文件缺失或小于 40 MB 时，`transcribeWhisper()` 返回 `null`，自动回退到
  System.Speech，不会让整条语音链路不可用
- ffmpeg 滤镜里的路径要转义：反斜杠换正斜杠、冒号前加反斜杠、整体用单引号包住
- `run()` 现在带 `cwd: WORK_DIR`，所以 `destination` 用相对文件名即可，
  避免在滤镜串里塞带空格的绝对路径

### 抗噪与纠错实测（2026-11-02 凌晨）

用同一句话造了六种变体（`_app/_test/asr-variants/`），全部喂给 `/api/asr-legacy`：

| 变体 | 识别结果 | 耗时 |
|---|---|---|
| 原音 | 大肥鱼你好,今天要做什么?你不想要我去找你吗? | 3225ms |
| 小声 -12dB | 大肥鱼你好 今天要做什么 你不想要我去找你吗? | 2651ms |
| **极小声 -18dB** | **大肥鱼你好 今天要做什么 你不想要我去找你吗?** | 2741ms |
| 电话音质（200–3400Hz 带通） | 大肥鱼你好,今天要做什么?你不想要我去找你吗? | 2395ms |
| 快 1.25x | 大肥鱼你好今天要做什么 | 3184ms |
| 慢 0.85x | 大肥鱼你好,今天要做什么? | 3183ms |

**结论一：音量完全不是瓶颈。** 负 18dB 依然全对——真人再怎么小声都够用。

**结论二：变速会丢句子，但那是 `atempo` 失真，不代表真人语速。**
去掉 VAD 后照样丢，所以不是 VAD 切掉的。真人说话不会被重采样扭曲，不用为这个改参数。

### 名字纠正：三种错法

| 错法 | 例子 | 成因 |
|---|---|---|
| 大肥X | 大肥云 / 大肥宇 / 大肥與 | 同音字 |
| **大佛X** | 大佛云 | 声母 f 对调 |
| **大飛X** | 大飛云 | 拼音近 |

正则三条并列放在 `FIXUPS` 里。注意**不能只写 `大肥[云…]`**——「大佛云」开头就不是「大肥」，
必须单列一条 `大佛[云魚鱼玉宇]`，否则永远不会被纠正（这个坑踩过一次）。

### 繁体收敛

whisper 中文常吐繁体。加了 12 组常用字映射：`什麼/這麽/那麽/說/與/現在/時間/麼/嗎/們/這/個`。
只换独立字，不动词义。

### 幻觉清理

`(字幕:J Chong)` 是 whisper 把噪声翻成字幕署名的训练数据残留。两条正则：
```
[/[(（]\s*字幕[^)）]*[)）]/g, ''],
[/[(（][A-Za-z][^)）]{0,12}[)）]/g, ''],
```
实测能清干净，不留残渣。

## 十三、桌面「手机远程服务」面板（2026-11-06）

DSH 桌面左侧那个「手机远程服务」小面板由 `../plugins/dsh-phone-bridge/` 提供，分两半：

- `index.js`（宿主端）：注册 `/dsh-phone-api/status|start|port|stop|paircode`，负责真正拉起/杀掉桥接；
- `client.js`（页面端）：输入框 dock 区的「远程服务」按钮和面板，5 秒轮询一次状态。

### 面板可拖动

面板默认在左下角，**按住标题栏即可拖到任意位置**，松手后位置存进
`localStorage['dsh.phone.panel.pos']`，刷新/重启后还在；窗口变小或手机横竖屏切换会自动
夹回视口内，不会拖丢。**双击标题栏回到左下角**并清掉记录。拖动用 Pointer Events +
`setPointerCapture`，鼠标、触屏、手写笔都通用；标题栏设了 `touch-action:none`，拖动时不会
带着页面一起滚。

### 「bad json」是怎么来的

面板报 `bad json` 不是 `runtime/state.json` 坏了，而是页面端 `fetch('/dsh-phone-api/status')`
拿到了 HTML 404（宿主端路由没挂载），`r.json()` 解析失败后兜底成这句话。
宿主端要挂载，`~/.dsh/profiles/desktop/package.json` 里必须同时满足：

1. `dsh.profile.bundles` 列了 `@local/dsh-phone-bridge`；
2. `dependencies` 里也有 `"@local/dsh-phone-bridge": "file:../../plugins/dsh-phone-bridge"`；
3. `node_modules/@local/dsh-phone-bridge/index.js` 真实存在。

只在 bundles 里写、不在 dependencies 里声明时，下一次 `pnpm install` 会把它当多余包移到
`node_modules/.ignored/`，宿主路由就没了；把 `.ignored` 里的目录复制回 `node_modules/@local/`
并在 dependencies 补一行即可恢复。宿主端 `index.js` 改动需要重启 DSH 桌面应用；页面端
`client.js` 由 `/plugins/events` 的 500ms 轮询热重载（刷新页面也可），本次实测服务端返回的
bundle 已含 `PANEL_POS_KEY`。

`npm run doctor` 会检查这三项，缺了直接亮红灯；`tests/plugin.test.mjs` 用假 ctx 验证
五个路由都注册、`/status` 返回的确实是 JSON，避免再出现「面板在、接口没了」。

## 十四、语音输出引擎：Edge / 肥鱼 CosyVoice3 / 系统音色

设置页最上面一排「引擎」按钮决定手机播报用哪条链路，**它和音色是两件事**：
先选引擎，音色列表只显示这个引擎支持的项。桌面和手机共用同一份 `state.ttsEngine`。

| 引擎 | 音色来源 | 联网 | 特点 |
|---|---|---|---|
| `edge`（默认） | 微软 Edge TTS 的 9 个中文音色 | 要 | 快、稳、零安装；断网会回落系统音色 |
| `feiyu` | 本机 `D:\feiyu` 的 CosyVoice3，音色=references 目录里的参考音频 | 不要 | 本机 GPU 推理，能克隆音色；首次加载约 9 秒 |
| `onecore` | Windows 自带的 Huihui/Yaoyao/Kangkang/Zira/David | 不要 | 最后兜底，音质一般 |

### 肥鱼引擎怎么起

```powershell
# 根目录，双击也行
.\启动肥鱼语音.bat            # 后台启动并等 /health ready
.\启动肥鱼语音.bat console    # 前台跑，能看日志
.\启动肥鱼语音.bat status
.\启动肥鱼语音.bat stop
```

服务是 `tools/feiyu-tts-service.py`，只监听 `127.0.0.1:8898`，令牌写在
`runtime/feiyu-tts/service.json`（手机桥读它来调服务，所以两边都不需要手填密钥）。
Python 用 `D:\feiyu\venv`，不装全局包；Windows 原生跑，不需要 WSL。

### 音色 = references 目录

**不再硬编码音色表。** 服务启动时扫
`D:\feiyu\models\FeiyuVoice-CosyVoice3\references\*.wav`，要求同名 `.txt` 提供参考文本；
每个 wav 就是一个音色，改动后重启服务即可生效（也可 `POST /warmup` 触发重扫）。

- 公开 id 用固定别名：`可爱→cute`、`温柔大姐姐→gentle`、`小鲸鱼→whale`、
  `八重神子→yae`、`菲比→phoebe`、`弗洛洛→fururu`、`卡芙卡→kafka`；
  新文件名会自动 ASCII 化，中文名则给 `style-<hash6>`，手机端显示的还是原始中文名。
- manifest 里同名风格若带 `llm_checkpoint`（例如 `cute` → `feiyu_cute_F6_0040.pt`），
  就用那份精调权重；其余共用 base `llm.pt`，切换时**不重复加载**。
- 参考音频换了不会串音：缓存 key 里带 `sha1(文件名|大小|mtime)` 前 12 位，
  旧音频自动失效。
- 缺 `.txt` 的 wav 会被跳过并在 `/health.skipped` 里列出来，不影响其它音色。

命令行验证（不开手机也能测）：

```bash
node tools/feiyu-check.mjs            # 只查健康与音色表
node tools/feiyu-check.mjs --synth    # 每个音色各合成一句，打印耗时/时长
node tools/feiyu-check.mjs --style=kafka --text="随便说一句"
```

### 回落规则（不会因为引擎挂了就没声）

`tts.mjs` 的 `resolveEngine()` 先保证「引擎与音色同族」：选了肥鱼却拿着 Edge 音色，
会自动换成肥鱼默认音色，反之亦然。运行期失败再按链路回落：

```
feiyu 失败 → Edge（响应里带 feiyuError，手机端只在控制台提示）→ onecore
edge  失败 → onecore
```

所以「肥鱼服务没开」只会让声音变成 Edge，不会报错给用户。
分段并发也按引擎区分：Edge 可以 2 段并行，肥鱼固定 1 段（一张显卡，排队比抢显存快）。

### 实测（RTX 4060 8G，本机）

| 项目 | 数值 |
|---|---|
| 模型加载（冷） | 8.5–9.8 s |
| 单句 4–6 秒音频 | 4.0–6.4 s（含切分/拼接） |
| 服务端缓存命中 | 50–60 ms |
| 手机桥缓存命中 | 17–60 ms |
| 7 个音色批量冒烟 | 7/7 通过，3955–6372 ms/句 |

### 接口

```bash
# 看引擎与音色
curl "http://127.0.0.1:8899/api/voices?t=$TOKEN"

# 只切引擎（会自动选中该引擎默认音色）
curl -X POST "http://127.0.0.1:8899/api/voice?t=$TOKEN" \
  -H 'content-type: application/json' -d '{"ttsEngine":"feiyu"}'

# 合成（不传 engine 就跟随 state）
curl -X POST "http://127.0.0.1:8899/api/tts?t=$TOKEN" \
  -H 'content-type: application/json' -d '{"text":"你好呀","voice":"feiyu-cute"}'
```

返回体里的 `engine` 是**实际使用**的引擎（可能因回落与请求不同），`feiyuError` 非空
说明这次是从肥鱼回落的。

## 十五、摄像头与直播：让他看见世界（2026-11-15）

一句话：手机端多了一双眼睛。你按一下快门，他立刻看见这一眼；你开直播，他每隔一会儿
自己看一眼，看到的画面**真的出现在会话里**（以「我」发出去的一张照片），他的点评就长在
照片下面。核心工具是 MCP 里的 `phone_see`，它把手机的帧作为图片块交给模型。

### 15.1 三条通路

| 通路 | 谁发起 | 走的路 | 用在哪 |
|---|---|---|---|
| 手动一眼 | 你按快门 | 抓帧 → `/api/upload` → 当作附件 `/api/send` | 「让他看」面板 |
| 直播点评 | 你开直播 | 抓帧 → 上传 → `POST /api/live/comment` | 画面挂在会话上方，点评长在会话里 |
| 主动看 | 模型 | MCP `phone_see` → `/api/camera/latest` | 任何 DSH 会话里调 `mcp__phone__phone_see` |

抓帧优先走**浏览器视频流**（`getUserMedia` + canvas），拿不到才退到原生 Camera2
（`NC.grab()`）。APK 里已经放行了相机权限，所以 WebView 里的 `getUserMedia` 是可用的。

### 15.2 手机端怎么用

- **让他看**：底栏 📷 → 面板里三格：相册 / 快门 / 直播。按中间圆就是一次「现在」，
  照片自动发给他；面板的朝上胶囊会写「后置 · 朝外」或「前置 · 对着你」。
- **直播**：点面板里的「直播」——面板收起，画面**挂到会话上方**（不再是一个盖住聊天的
  浮层），下面能正常看消息。右上「停止」收起画面并放开相机。
  间隔在画面下方选（10 秒 / 20 秒 / 30 秒 / 1 分钟 / 2 分钟），选完立刻同步给服务端。
- **相册**：复用系统文件选择，图片同样带绝对路径进附件。

### 15.3 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/camera/push?mime=image/jpeg&w=&h=&facing=` | 一帧进环形缓冲（默认 12 帧，`PHONE_CAM_BUFFER`） |
| GET | `/api/camera/latest?n=1..9&timeout=&maxAge=&since=` | 取帧，返回 `{frames:[{n,ts,mime,b64,w,h,facing}],stale,ageMs}` |
| GET | `/api/camera/arm?timeout=25000` | 挂起等一句「AI 要一眼」，帧到了才回 `{grab:true}` |
| POST | `/api/camera/live` | `{on,fps,gapMs,facing}` 取景开关 + 点评间隔 |
| GET | `/api/camera/state` | `{frames,seq,arm,waiting,ageMs,totalPushes,live,size}` |
| POST | `/api/live/comment` | `{k,path,size,mime}`：把这一眼入队（带图） |

`/api/live/comment` 的三道闸：

- **限流**：距上一眼不足 `gapMs - 800ms` → `429 {waitMs}`（客户端必须按 `waitMs` 排下一次，
  固定 `setInterval` 会在边界上必撞）
- **无新帧**：缓冲里没有帧或最新帧超过 `PHONE_LIVE_FRESH_MS`（默认 7 秒）→ `409`
  —— 宁可这一眼跳过，也不许把旧帧当现在讲
- **排队**：已经有一条在等 → `202 {skipped:'busy'}`，不当失败

### 15.4 MCP 工具 `phone_see`

```
phone_see(n=1..9, fresh=true, timeoutMs=9000)
```

返回**一条文字 + n 个 `image` 内容块**（`mimeType: image/jpeg`，规范 base64）。
`dsh-mcp-client` 会自动把它们转成 attachment，模型直接看见。文字的抬头会写清朝向
（`user` = 前置，大概是主人自己；其他 = 后置朝外）、每帧尺寸，以及 `ageMs`；
拿到的不是新帧时会明说「不是刚拍的」。

手机没开取景时不要编画面 —— 工具会返回一句说明，照它说就行。

### 15.5 APK 权限与原生兜底

- `AndroidManifest.xml`：`CAMERA` + `<uses-feature android:required="false">`
- `MainActivity`：`onPermissionRequest` 放行 `RESOURCE_VIDEO_CAPTURE`；
  `grantWebPermission()` 拿不到权限时先 `requestPermissions(CAMERA, REQ_CAM)` 再 grant
- 原生兜底：`grabFromView(TextureView)` 直接从**正在跑的预览纹理**抠一帧
  （`getBitmap` → JPEG），所见即所传；`pickJpegSize()` 从机型支持的 JPEG 尺寸里挑，
  避免写死 1280×720 导致 `acquireNextImage` 永不回调
- 取景器是按页面给的矩形贴上去的：`startPreview(l,t,w,h)`，所以要等抽屉滑动动画结束再量坐标

### 15.6 这一层踩过的坑

1. `readBody()` 返回 utf8 字符串，收二进制必须用 `readRaw()`，否则帧被毁成乱码
2. `ImageReader` 的 JPEG 尺寸必须落在机型支持列表里，否则**预览正常、抓帧永远空**
3. 服务端缓冲带 `ageMs`：没有新帧时宁可不点评，也不许拿旧帧当现在（这条是被真实误报逼出来的）
4. 客户端必须按服务端返回的 `waitMs` 排下一眼；`setInterval` 会在限流边界撞 429
5. 前端事件白名单 `BUS_EVENTS` 漏了 `delta` / `turn_end` → 直播流永远空白（虽然服务端在广播）
6. `TextureView` 是贴在 WebView 上面的浮层：面板一关就必须 `stopPreview()`，
   否则退出后画面还盖着会话（现在是「停止」按钮统一收口）
7. `#cam.native .cambox{display:none}` 这种规则会让取景框整块消失，
   DOM 层面看不出来，只有截图能发现

### 15.8 直播设置（⚙）

直播条右上角的 ⚙ 打开设置，四项都能随便调，改完立刻生效、存在手机本地：

| 项目 | 范围 | 说明 |
|---|---|---|
| 他多久看一眼 | **5 秒 – 10 分钟**（滑杆 + 常用档位 5s/10s/30s/1min/5min/10min） | 太密他来不及说话，太疏会错过变化 |
| 画面大小 | 流畅 640 / 标准 960 / 高清 1280 / 原图 1920（长边像素） | 越大越清楚，传得越慢越费流量 |
| 压缩质量 | 40% – 95%（JPEG） | 要看清字用 85% 以上 |
| 状态行显示什么 | 尺寸 + 大小 / 只说第几眼 | 想省点视觉噪音就只报第几眼 |

**两条抓帧路径的输出是统一的**：浏览器视频流直接按 `画面大小` 出图；原生相机给的帧是它
自己的尺寸，会过一次 `recode()` 再压到同一档，所以换路径不会突然变糊或变大。

服务端这一侧：`POST /api/camera/live` 的 `gapMs` 夹在 **5000–600000**，
`/api/live/comment` 的限流余量是 `gap - 800ms`；间隔改大以后，取景流会一直开着，
费电，但每一眼都是当场的画面（点「停止」才真正释放相机）。

出问题时状态行会自己说清楚走的是哪条路，例如
`这一眼没拍到（走的是原生取景）：镜头被别的应用占着` ——
`浏览器直取` / `原生取景` / `一秒一张` 三种来源一眼可辨。
### 15.9 相机自检（⚙ 里那颗「测一下现在的画面」）

抓不到帧这种事不该让主人替我复述。设置面板最下面那颗按钮按一下，就用**当前设置**抓一帧，
结果写在按钮下面那一行，同时记到服务端：

```
拿到了：640×480 · 8KB · 115ms · 原生取景
没拿到画面（走的是浏览器直取）：权限被拒了。到浏览器/系统设置里放行这个站点的相机
```

`GET /api/camera/state`（以及 `/api/health`）里的 `probe` 就是这条记录：

```json
{ "ok": true, "src": "原生取景", "w": 640, "h": 480, "kb": 8, "ms": 115, "at": 1794…, "ageMs": 1200 }
```

`src` 只有三种：`浏览器直取`（getUserMedia + canvas）、`原生取景`（Camera2 帧 / 预览纹理抠帧）、
`一秒一张`（取景器开不成时的保底轮询）。**直播第一眼成功时也会自动写一条**，
所以哪怕主人只是开了直播没点自检，`/api/camera/state` 里也有证据。

排查顺序就照着 `src` 与 `why` 走：
`浏览器直取` 失败 → WebView 的 `onPermissionRequest` 或 https 上下文；
`原生取景` 失败 → 相机被别的应用占着、或 `pickJpegSize()` 又挑到了不支持的尺寸。
### 15.10 APK 侧的两处硬化（2026-11-15 晚）

1. **启动就申请相机权限**：`MainActivity.onCreate` 里先要一次 `CAMERA`。
   等到用户按快门再弹窗，很容易被当成「点了没反应」——浏览器那条路
   （`getUserMedia`）和原生那条路（Camera2）都要这个权限，先要到手最省事。
2. **等画面真的出来再抓**：摄像头流刚开时 `videoWidth` 还是 0，这时候抓帧只会拿到一张空图。
   现在 `waitVideo()` 会等到 `videoWidth > 0`（最多 2.5 秒）再抓，
   抓不到就明说「摄像头流开着，但画面还没出来（videoWidth=0）」，
   不再笼统报「没有取到帧」。
### 15.11 自动换路（1.5.1）

抓帧有三条路，任何一条断了都不该让你自己去猜：

```
浏览器视频流（getUserMedia + canvas）
  → 原生取景器（Camera2 + TextureView，所见即所传）
    → 一秒一张（定时向原生要帧）
```

- 连着**两眼下不来**，就自动换下一条，状态行会写「这条不对（原因），换成下一条…」
  然后「一秒一张 · 已经换过来」。
- 换路之前会先把上一条收拾干净（停轨道、收取景器、清定时器），不会两条路同时占着相机。
- 三条都不行才说「三条路都拿不到画面：原因」，并且原因具体到
  `videoWidth=0` / `没有相机权限` / `镜头被别的应用占着` 这种级别。
### 15.12 上传 / 分享前：仓库里不许有你的地址和令牌

这台机器上的真实入口、服务器 IP、令牌，一个都不能进公共仓库。现在是这样隔离的：

| 东西 | 放哪 | 进仓库吗 |
|---|---|---|
| APK 的公网入口 | `android/local.properties`（`dsh.public` / `dsh.legacy`） | 不进，仓库只留 `local.properties.example` |
| 手机通道令牌 | `phone-bridge/runtime/state.json` | 不进（`runtime/` 已忽略） |
| 测试台截图（含真实对话与照片） | `phone-bridge/test/out/` | 不进 |
| 隧道配置 | `phone-bridge/tunnel.json` | 不进 |

构建时 `pbuild.ps1` 读 `local.properties`，生成一个不入库的
`java/com/dsh/phone/BuildConfig.java` 再编进去 —— 所以谁 clone 这个仓库都能编译，
但编出来的包指向的是 `https://dsh.example.com/dsh`（示例），只有本机配了真地址才指向真的。

上传前跑一次闸门：

```powershell
node scripts/scrub-check.mjs        # 有命中就 exit 1
node scripts/scrub-check.mjs --list # 只列出来看看
```

它查：公网隧道域名、裸 IP 入口、32/40 位以上十六进制令牌、`C:\Users\<你的用户名>`、
私钥块、`?t=<令牌>` 这种命令行残留。示例域名（`dsh.example.com` / `example.com`）和
文档 IP（`203.0.113.x`）放行，免得闸门变成噪音。

**注意历史**：旧提交里带着过去的令牌与域名，`git push` 整个历史就会把它们一起送上去。
要发布就推一个干净的单提交分支（`scripts/publish-clean.sh` 的做法），不要推旧历史。

### 15.13 一轮卡住不会把直播拖死

- 单轮上限 `PHONE_BRIDGE_TURN_TIMEOUT_MS`（默认 8 分钟）。到点会中止子进程，并且在会话里
  说一句「这一轮超过 N 分钟还没结束，我先中止了」，不会让手机一直停在「他还在想…」。
- 直播那一侧只看**队列里有没有在排的一眼**，不因为管线忙就整轮放弃。
### 15.14 令牌失效长什么样 / 宽表格不再撑破排版（1.5.2）

- **换了令牌之后，旧手机不会再「一片空白」**：任何接口返回 401，页面就直接弹一张卡
  「这条连接已经失效了」，说明是令牌换过了、并用新地址重开。历史记录并没有丢，
  `runtime/messages.jsonl` 一直在，只是旧令牌取不到。
- **会话里的宽表格**：AI 回答里贴进来的表常常一千多像素宽，以前会把整页顶宽，
  手机上表现为「排版全乱、右边被切」。现在表格和代码块各自在气泡里横向滚动，
  页面宽度永远等于屏幕宽度（390 宽实测 `docScrollWidth = 390`）。
- **一个撞 id 的按钮**：直播设置面板的 ✕ 和旧设置面板的 ✕ 用了同一个 `cfg-close`，
  结果旧面板那个按钮点了没反应、页面自检横幅常驻。现在直播面板那个叫 `livecfg-close`。
### 15.15 为什么「画面看得见、帧却抓不到」（1.5.2）

这条查了很久，最后落在 **Android 的线程规定**上，而不是相机本身：

- `WebView.evaluateJavascript()` 只能在**主线程**调用。相机回调（`ImageReader` / `onCaptureCompleted`）
  和 `JavascriptInterface` 的方法都不在主线程上，直接调会被 WebView 拒掉；
  而我们的 `jsCall()` 外面套着 `catch (Exception ignored)`，异常被吞掉 → **一点痕迹都没有**。
- `TextureView.getBitmap()` 同样必须在主线程 —— 从相机线程调，常常直接返回 `null`。

所以现象是：预览是 `TextureView` 常开会话，画面一直有；可「抓帧 → 送 JS」这一段永远断在半路，
页面等着 `__camFrame` 永远等不到，只能说一句「没有取到帧」。而**拍照能用**，是因为它走
`ACTION_IMAGE_CAPTURE`，结果回到 `onActivityResult`（本来就在主线程）。

现在的写法：`jsCall()` 一律 `ui.post(...)`；`camDone()` 整块收拢到主线程；
`grabFromView()` 若不在主线程，就投递一段到主线程并用 `CountDownLatch` 等 3 秒取结果
（`grabFromViewOnUi()` 才是真正 `getBitmap` 的那一半）。

自查方式：装新 APK 后开一次直播，若还拿不到帧，状态行会写「这一眼没拍到（走的是原生取景）：…」，
同时 `GET /api/camera/state` 里的 `probe` 会留下 `ok/src/w/h/kb/why`。
### 15.16 「自检」现在逐条报路（1.5.2）

以前那条「测一下现在的画面」只测**当前正在走的那条路**，所以一台机器上到底哪条能出画面
仍然要猜。现在点一次会把三条路各跑一遍，结果直接写在面板上，同时存进
`GET /api/camera/state` 的 `probe.steps`：

```
浏览器 ✓ 1180ms · 原生 ✗ 6000ms   （原生：6 秒没有回调（相机没给帧））
```

| 步骤 | 怎么测 | 失败意味着 |
|---|---|---|
| 浏览器 | 临时 `getUserMedia` → 等 `videoWidth>0` → 停流 | 不是 https / 没权限 / WebView 没放行 |
| 原生 | 直接调一次 `DSHCam.grab()`，最多等 6 秒回调 | 没有 APK 桥，或相机没给帧 |

另外：**一眼没拿到帧就立刻换下一条路**（以前要连着两眼，一眼 20 秒，等于要等 40 秒才发现不对）。
成功那行也会带上走的是哪条路：「第 3 眼看过了 · 浏览器直取 · 1280×720 · 10 KB · 21:22」。
### 15.17 它自己记得哪条路能出画面（1.5.3）

抓帧有三条路：浏览器 `getUserMedia` → 原生取景 → 一秒一张。原来每次都从第一条开始试，在一台只能走原生的机器上，等于每次开播先白等一轮失败。

现在会把**成功过的那条**记在 `localStorage['dsh.liveSrc']`，下次开播先走它；中途换路换成功了也更新这条记录。想强制重试顺序，清掉这个键即可（浏览器控制台 `localStorage.removeItem('dsh.liveSrc')`）。

配套三处「不要让人对着空气等」：

| 情形 | 现在的表现 |
| --- | --- |
| 一眼没抓到帧 | **立刻**换下一条路，并写明「这条不对（原因），换成原生取景…」 |
| 换过去也不成 | 「换到原生取景也没成，接着试下一条…」→ 最后「三条路都拿不到画面：原因 · 修好再点开播」并**停下**，不再每 5 秒撞墙 |
| 服务端 30 秒没收到新帧 | 会话里自动出现一条系统提示：「已经 30 秒没有画面送过来了…点齿轮 →「测一下现在的画面」」 |

### 15.18 自检说人话（1.5.3）

齿轮里的「测一下现在的画面」现在**逐条报路**，不再只报当前这一条：

```
浏览器 ✓ 1180ms · 原生 ✗ 6000ms（6 秒没有回调）
```

同一份结果也存进 `/api/camera/state` 的 `probe.steps`，所以远程也能读到「哪条通、哪条不通、多久放弃、为什么」。
### 15.19 打不开相机时，给一张能照着做的卡片（1.5.4）

三条路全灭时不再只丢一行状态字，直播条里会展开一张卡片，按原因给步骤：

| 原因 | 卡片上怎么说 |
| --- | --- |
| `NotAllowedError` / 权限被拒 | 地址栏左边的小锁 → 网站设置 → 摄像头 → 允许；在 App 里去 系统设置 → 应用 → DSH Phone → 权限 → 相机 |
| `NotReadableError` / 被占用 | 先把别的用相机的应用（相机、视频通话、扫码）关掉 |
| `NotFoundError` / 没有相机 | 这台设备没有可用的后置相机，或系统没交给浏览器 |
| 其它 | 直接写原因，并提示用 https 打开 |

卡片上两个按钮：**再试一次**（重新走三路）、**先收起**。

### 15.20 不叠请求（1.5.4）

一眼还在路上时，下一拍直接跳过并在设置面板里记「跳过 N 次」，不把请求堆起来（dsh-see-world 里同一套思路，它记的是 `dropped`）。
### 15.21 取景层跟着页面走，退出就一定收掉（1.5.5）

第二条路（原生）用的是贴在直播框上的原生取景层。它不会跟着页面滚动，所以：

| 以前 | 现在 |
| --- | --- |
| 开的时候给一次坐标，页面一动就脱位，看着像「盖在会话上面」 | 页面滚动 / 窗口尺寸变化 / 内容变化都会重新报一次矩形，原生**只挪位置、不重开相机** |
| 退出直播若 JS 没来得及喊停，那层就留在原地 | `stop()` / `teardownPreview()` 一律走 `closeOverlay()`：`stopPreview()` + 摘掉监听；原生侧 `stopLive()` 会 `removeView` |
| 退到后台还开着相机 | 原生 `onPause()` 里已经 `stopLive()`（早就有） |

想让原生改成「逐帧取图」（不贴层，帧画进 `<img>`）：`localStorage.setItem('dsh.liveOverlay','0')` 后重开播。逐帧那条每次都要自己开一次相机会话，慢一些，只在取景层开不成时用。

顺带修掉互相覆盖的坑：直播期间原生帧不再往服务端缓冲推原始尺寸（会把用户设的 640 宽覆盖回 1280），缓冲统一由直播那条按画质推。
### 15.22 参数范围放宽（1.5.6）

| 参数 | 原来 | 现在 | 上限受什么约束 |
| --- | --- | --- | --- |
| 多久看一眼 | 5 秒 – 10 分钟 | **2 秒 – 30 分钟** | 越快越费电、越容易被服务端 429 节流；低于 2 秒没有意义 |
| 画面长边 | 640 / 960 / 1280 / 1920 | 加 **480 省流**、**2560 超清** | 夹取 320–2560；手机后置一般也就 4:3 的 4000+，超过 2560 只是白传 |
| 压缩质量 | 40% – 95% | **20% – 98%** | 低于 20% 字都糊了；98% 一张能到 1 MB+ |

页面与服务端两侧的夹取都跟着放宽了（`setCad()`、`QUALITY`、`/api/camera/live`、`/api/live/comment` 一致），不会出现「面板能拖、发出去被悄悄压回旧值」。

同时修：取景层开播那一瞬间会量到 0 尺寸（直播条还没展开），原来直接放弃 → 6 秒没有一帧。现在会在 1.8 秒内反复量，量到才报给原生；等帧时间放宽到 8 秒（要给权限弹窗留位置）。
### 15.23 一次自检，把「哪儿坏了」和「拍到了什么」一起交回来（1.5.7）

以前自检只报「拿到了 / 没拿到」，出问题还得靠猜。现在点一次「测一下现在的画面」，会一起交回去：

| 交回去的东西 | 用来看什么 |
| --- | --- |
| 每条路的判定 + 耗时 | 浏览器 `getUserMedia`、原生 `DSHCam.grab` 到底哪条通 |
| 失败原因原文 | `NotAllowedError`（没给权限）/ `NotReadableError`（被别的应用占着）/ `NotFoundError`（没有相机）… |
| 真机环境 | UA、是否安全上下文（https）、权限状态、屏幕与 DPR、原生桥在不在 |
| **那一帧原图** | 存成 `runtime/probe-last.jpg`，`GET /api/camera/probe/shot?t=<令牌>` 直接取回来看 |

也就是说：手机那边点一下，电脑这边就能看到「他到底拍到了什么」，不用人复述、也不用猜。

顺带修：取景层开播那一瞬间会量到 0 尺寸（直播条还没展开），原来直接放弃 → 6 秒没有一帧；现在 1.8 秒内反复量，量到才报给原生，等帧时间放宽到 8 秒（给权限弹窗留位置）。
### 15.24 逐帧模式改成串行排队，原生桥报版本（1.5.8）

- 「一秒一张」以前是 `setInterval` 硬排：上一帧还没回来就再撞一次，原生那边只会回「上一帧还没回来」。现在改成**串行**：这一帧回来才排下一拍，间隔里先问 `DSHCam.busy()`，忙就跳过这一拍。
- 原生桥新增三个只读方法：`version()` → `cam2/1.5.8`、`busy()`、`hasPermission()`。自检上报的 `env.build` 就是 `version()`，以后一眼就知道装的是哪版 APK、权限到底给没给。
- 取景层开播时反复量矩形（1.8 秒内），量到才报给原生；等帧时间 8 秒。
### 15.25 面板里能算出这套设置要花多少流量（1.5.8）

抓完一帧就知道它多大，于是设置面板直接把账算给你看：

- 压缩质量下面多一行灰字：`每眼约 26 KB · 一分钟约 78 KB（按现在的设置）`。
- 数是真的：用最近一帧的实际字节数 × 当前间隔换算，不是拍脑袋的估值。
- 调间隔、调质量、换长边，这行立刻跟着变——想省流量就把这三样往下压。

### 15.26 自检那一帧，电脑这边直接能看（1.5.7 起）

手机点「测一下现在的画面」，除了三条路的成败，还会把**那一帧 JPEG 一起传回来**：

```bash
# 在电脑上取回手机刚才拍到的那一帧
curl -s "http://127.0.0.1:8899/api/camera/probe/shot?t=<令牌>" -o probe-shot.jpg
```

`/api/camera/state` 里的 `probe` 同时带着 `env`（安全上下文、权限、DPR、视口、原生桥版本、UA）与 `shot.bytes`。
排查顺序：先看 `env.secure` 是否 `true`（不是 https 就没有摄像头）、`env.perm` 是否 `granted`、
`env.native` 是否 `true`（APK 里应该是），再看两条路谁 ✓。
### 15.27 面板里逐条记着「最近那几眼」（1.5.9）

直播跑起来之后，设置面板多一块灰底小字，最近 8 眼逐条写在这里：

```
00:31:26  ✓ 8 KB · 一秒一张
00:31:31  ✓ 26 KB · 原生取景
00:31:48  ✗ 原生取景 · 相机没给画面：镜头被别的应用占着
```

- 成功的记：时间、这一帧多大、走的是哪条路。
- 失败的记：时间、哪条路、为什么（原话，不加工）。
- 点「测一下现在的画面」时，这份记录会跟自检结果一起送到电脑（`/api/camera/state` 的 `probe.recent`）。

另外：如果手机上的 App 还是旧版（原生桥没有 `version()`），点开播会直接弹一张卡说明「手机上的 App 还是旧版」并指向 `/apk`——不用再猜是不是权限问题。
### 15.28 在 App 里用内网地址打开时，直接请你换 https（1.5.10）

手机连着的如果是 `http://10.x.x.x:8899` 这种内网地址，浏览器**根本不会**把摄像头交给页面（安全上下文限制），
于是只剩 App 的原生取景，画面就容易断、也容易「有画面但没截到帧」。

现在点开播时，页面会自己发现这件事，弹一张卡：

> **这个地址拿不到摄像头**
> 你现在用的是 http 内网地址……换个入口重新打开一下，令牌会一起带过去。
> `[用 https 打开]` `[再试一次]` `[先收起]`

- 「用 https 打开」跳的是打包时写进 APK 的 `BuildConfig.DEFAULT_PUBLIC`（`android/local.properties` 的 `dsh.public`）。
- 令牌自动带过去（`?t=<当前令牌>`），重新打开后不需要再配对。
- 原生桥新增 `entry()` 只读方法提供这个地址；版本走到 `cam2/1.6.0`。
- 这条提醒优先级高于「相机没能出画面」的通用卡片——同一件事不重复说两遍。
### 15.29 自检现在会把那一帧摆给你看（1.5.11）

设置面板的「测一下现在的画面」按下去之后，面板里会多三行：

1. **两条路各自的判定**：`浏览器 ✗ 634ms · 原生 ✓ 134ms（浏览器：NotAllowedError）`
2. **这一帧本身**（缩略图，就是准备发出去的那张 JPEG）
3. **环境**：`https ✓ · 权限 denied · 原生桥 cam2/1.6.0 · 390×844@2`

这样「有没有截到帧」不用再猜——**图在，就是截到了**；图不在，上面那行会写清是哪条路、什么原因。
这张图同时会存进服务端（`/api/camera/probe/shot`），电脑这边直接取回来看。
### 15.30 打开就会自己验一次；收画面这件事排在第一位（1.5.12）

- **静默自检**：页面打开 7 秒后自己跑一次「三条路各试一遍 + 抓一帧」，结果连图一起送回 `/api/camera/probe`，每天只跑一次（`localStorage['dsh.autoProbe']` 记日期），直播进行中不打扰。这样主人什么都不用点，电脑这边就能看到他手机上的真实情况。
- **`stop()` 顺序加固**：以前是「先告诉服务端、再收画面」，万一中间那步网络报错，取景层就留在屏幕上了（正是「退出直播还盖着」的那种）。现在**第一件事就是 `closeOverlay()`**，其余步骤全部 `try/catch` 包住；`visibilitychange` / `pagehide` 仍会自动收，Android 侧 `onPause`/`onDestroy` 也会 `stopLive()`。
### 15.31 APK 启动时把内网 http 配对自动迁到 https 入口（原生桥 1.7.0）

`http://10.x.x.x:8899` 这种地址，浏览器不会把摄像头交给页面（安全上下文限制），手机就只剩原生取景一条路。
新包在启动时做一件事：**只要内置了 https 入口（`BuildConfig.DEFAULT_PUBLIC`），而上次配对的是 `http://`，就自动迁到 https**，令牌一起带过去，不用重新配对。

- 旧地址存进 `K_ALT`：万一 https 进不去，`onWebError` 会自动退回内网地址并置 `stayHttp = true`，之后启动不再往回跳。
- 手动想留内网：把 `stayHttp` 打开即可（或重新配对填内网地址）。
- 页面上那条「这个地址拿不到摄像头 → 用 https 打开」的卡片仍在，两条路都留了个出口。

### 15.32 三条路都不通时，至少还能拍一张（1.5.14）

直播可用的三条抓帧路（浏览器流 / 原生取景 / 原生逐帧）全都拿不到画面时，卡片上除了「再试一次」，
现在还多一个 **「拍一张给他看」**：它先收掉直播，然后打开那个**一直都在好好工作**的相机面板——
用系统相机拍一张，照片照旧以「我」的身份发进会话。

这样即使某台机器上直播这条路彻底不通，看世界的功能也不会整块失效：一次点击就退回到最稳的那条路。

### 15.33 取景层跟着页面走，看不到就藏起来（1.5.15 + 原生桥 1.8.0）

原生取景层是叠在网页上的一个原生 View，**不会跟着网页滚动、也不会被裁剪**。所以：

- 页面滚动 / 窗口变化 / 每秒 400ms 的兜底同步：重新把取景框摆到「直播框现在的位置」；
- 直播框一旦离开可视区（滚走、被页面挪走），立刻调 `DSHCam.setPreviewVisible(false)` 把它藏掉，
  回到视野再画上——不再出现「退出去之后画面还盖在会话上」；
- 停止直播一定先收这一层（`stop()` 第一句就是 `closeOverlay()`），并且用 `overlayGen` 让「关闭之后才到点的定时器」自动作废；
- 排障探针：`window.__liveState()` 返回 `{running, nativePreview, overlayTick, src, boxTop}`，一眼看出现在是不是走取景层、同步有没有在跑。

测试台 `[7b]` 段覆盖：开直播走取景层 → 把直播条挪出屏幕 → 断言收到 `setPreviewVisible(false)` → 挪回来 → 断言重新画上 → 停止 → 断言收掉预览。camtest 49/49。

### 15.34 取景层只管好看，给 AI 的那一帧照样抓（1.5.16）

以前有个隐蔽的坑：走原生取景层时，画面是「原生 View 自己在放」，页面以为「已经有画面了」，
于是**没有人再去抓帧**——屏幕上有画面、服务端缓冲里却没有，AI 那边就是「没有截取到帧」。

现在的分工很清楚：

- 取景层 = 预览：让画面丝滑、跟着页面走、离开视野自动藏；
- 抓帧 = 另一件事：每 5 秒无论到不到点，都悄悄抓一帧推进服务端缓冲；
  到点的那一眼照旧走 beat()：上传 + 让 AI 点评 + 在会话里以「我」发出。

另外两处小改：

- 原生取一帧的等待从 12 秒收到 **6 秒**（直播时一眼等 12 秒两次，看着就像卡死）；
- 取景层「藏起来」不再用 INVISIBLE，而是**挪出屏幕**（setTranslationY(-20000f)）：
  TextureView 一旦不可见就停止绘制，getBitmap 会拿到旧画面甚至 null。

### 15.35 App 里默认走「页面回放」，不依赖原生取景层摆位（1.5.17）

原生取景层是叠在网页上的一层原生 View：它不认裁剪、坐标要靠页面换算，
不同机型的状态栏 / 缩放一变，就可能出现「画面不在框里」甚至「盖在会话上」的样子。

所以 App 里的优先顺序改了：

1. **页面回放**（poll）：用原生抓帧、把帧画进页面里的 `<img>`——位置永远对，帧一定出得来；
2. 原生取景（native）：画面更顺滑，但依赖原生摆位，作为第二条；
3. 浏览器流（browser）：https 下最流畅，作为第三条。

浏览器里打开的顺序不变（浏览器流优先）。手机上想强制用取景层，可以设 `localStorage['dsh.liveOverlay'] = '1'`。
排障探针新增 `window.__liveOrder()`，直接看当前设备会用哪条路的顺序。

### 15.36 上传那条路不通时，这一帧跟着点评请求一起走（1.5.18）

直播每看一眼会先把图传到 `/api/upload`，再请求一次点评。真机上这两步之间会出岔子——
网络抖一下、网关挡一下、体积超一点，图就没上去；服务端只收到一句「看一眼」，
AI 只能说「这一眼没取到画面」，主人看到的又是「没截取到帧」。

现在改成：

1. 先照旧上传；
2. **上传失败就把这一帧（base64，≤1.6 MB）直接放进点评请求**（`data` 字段）；
3. 服务端收到 `data` 就当场落盘成 `workspace/uploads/live-<时间>-<第几眼>.jpg`，当作附件发给模型。

所以只要手机抓到了帧，AI 就一定看得到那张图 —— 传图这条路坏掉不再等于「什么都看不见」。
回归里也钉了两条：拦住 `/api/upload` 后，点评请求必须自带 JPEG（`/9j` 开头）。

### 15.37 端到端自证：模型确实收到了那一帧（1.5.18 验证）

`node test/live-once.mjs` 会真跑一轮：

1. 把 `test/out/probe-shot.jpg` 当新画面推进 `/api/camera/push`；
2. 发一条点评请求，**故意只带 `data`、不带 `path`**（等价于「上传那条路没走通」）；
3. 等模型回话，检查它说的是不是画面里的东西。

2026-11-16 实测三连：

| 次数 | 模型回的原话 |
| --- | --- |
| 1 | 「画面是一片纯蓝底，中间白色大字写着 phone-eye，看着像测试图，不是实景。」 |
| 2 | 「这一眼没拍到真实场景，只有一张蓝色背景、中间写着白字 phone-eye 的测试图……」 |
| 3 | 「画面里是纯蓝底，中间一行白色字 phone-eye，其余什么都没有，应该还在取景阶段。」 |

三次都准确描述了那一帧 —— 说明「手机抓到了帧 → 模型就一定看得到」，中间任何一条 HTTP 路断掉都不再等于看不见。

脚本会消耗一次模型调用（几秒到十几秒），所以没放进 `camtest`；只在需要端到端确认时手动跑。
注意服务端 `/api/state` 只保留最近 120 条消息，脚本靠「上一条 AI 说的话变了没有」判断新回复，不是靠数组变长。

### 15.38 电脑这边点一下，手机自己跑自检（1.5.19）

以前要看手机上的情况，得让主人去点设置面板里那个按钮。现在反过来：

```
curl -X POST "http://127.0.0.1:8899/api/camera/diag?t=<令牌>"
```

页面每 4 秒问一次服务端「有没有人叫我自检」，看到新请求就自己跑一遍三条路、
把结果和那一帧交回来。所以只要手机开着这个页面——哪怕在看会话、没开直播——
电脑这边发一次请求，十几秒后就能读 `/api/camera/state` 的 `probe`：

```json
{
  "ok": true, "src": "原生", "w": 640, "h": 480, "kb": 8,
  "steps": [{"n":"浏览器","ok":false,"why":"NotAllowedError"},{"n":"原生","ok":true,"ms":92}],
  "env": {"secure": true, "perm": "denied", "native": true, "build": "cam2/1.8.0"},
  "shot": {"bytes": 7794},
  "recent": "02:52:36 ✓ 8 KB · 一秒一张"
}
```

那一帧还能直接取：`GET /api/camera/probe/shot` → `image/jpeg`。

回归里钉了两条：请求下发得出去、页面自己跑完并回报（带着那几帧和每一路的原因）。

### 15.39 手机切到后台时，先说一声「我先不看」（1.5.20）

锁屏、切到别的 App、把页面压到后台——这时候抓帧必然断，但 AI 每 20 秒还是会叫一次「看一眼」，
然后回一句「这一眼没取到画面」。主人看到的，永远是「它又说没取到」。

现在页面自己会说：

- 切到后台 → `POST /api/camera/live/note {state:"hidden"}`
  - 服务端把直播标记成 `paused`，之后所有点评请求直接回 `409 paused`（不排队、不烧一次模型调用）；
  - 会话里留一句小字备忘：**「［手机把页面切到后台了（锁屏或切走了），这一眼先不看——回来我接着看。］」**
- 回到前台 → `{state:"visible"}` → 解除暂停，再留一句「［手机回到前台了，我接着看。］」

这些备忘是 `appendMessage` 直接落的（`kind: 'note'`），**不触发模型**，所以不花钱也不会打断正在说的话。

顺手改的两处：暂停判断放在「太密了」之前（否则暂停期间还会被 429 挡回来），
以及回归里 `[5d]` 四条断言：暂停生效、state 反映、点评回 paused、会话里有备忘。

### 15.40 逐帧取图的节奏跟着你设的间隔走（1.5.21）

以前「一秒一张」是死的：不管你把「他多久看一眼」设成 5 秒还是 30 分钟，相机都每秒开一次，
白烧电，还容易把相机拖到打不开（接着就是「没截取到帧」）。

现在 `pollGap() = 夹在 1 秒 ~ 15 秒之间(你设的间隔)`：

| 你设的间隔 | 逐帧取图 |
|---|---|
| 2 秒 | 2 秒 |
| 10 秒 | 10 秒 |
| 1 分钟 | 15 秒（封顶，够保鲜就行） |
| 30 分钟 | 15 秒 |

直播中直接拖设置面板也会立刻按新节奏重排，不用停一下再开。

### 15.41 原生自带一条直传：桥断了，画面也到得了电脑（1.5.22 / APK 1.9.0）

以前每一帧都要走这条链：相机 → 原生桥 → 页面 JS → 上传接口 → 电脑。
链条上任何一环静默失败，你看到的就是「没截取到帧」。

现在原生自己也有一条腿：开播时页面用 `NC.setUpload(https://<你的入口>/api/camera/push?t=<令牌>)`
把地址交给原生，之后**每拍到一帧，原生直接 POST 给电脑**（独立线程、8 秒连接超时、失败只在面板上说一句）。

- 页面那条路照旧走；两条路都到电脑时，服务端的缓冲只留最新一帧，不重复消耗。
- 退出直播会 `setUpload('')` 撤回，不会在后台偷偷传。
- 自检里 `pushLast()` 可以立刻把最近一帧传一次，不用等下一帧。

这条腿的意义：**即使 WebView 里的 JS 完全拿不到帧，电脑这边的「看一眼」也有画面可用。**

### 15.42 页面不管了，原生自己把画面收掉（APK 1.9.1）

取景层是叠在网页上的原生 View，它只认「页面报过来的矩形」——页面要是崩了、被系统挂起、
或者退出时那句 `stop()` 没跑到，这层就会一直留在屏幕上，看着就是「退出直播了画面还盖着会话」。

所以原生自己也放了一个看门狗：页面在管这层画面时会不停报位置（400ms 一次），
**一旦 6 秒没人报，就自己 `stopLive()` 把画面收掉**，并在面板上说一句「页面 6 秒没管这层画面了，我先收掉」。

- 只在「已经有取景层」时才可能触发；没开播时它什么都不做。
- 收到画面之后会把时间戳清零，避免连续触发。
- 每 2 秒看一次，2 秒精度内收干净。

### 15.43 直播条上的小灯：电脑收到没有，一眼就看见（1.5.23）

「没截取到帧」这句话最麻烦的地方，是你不知道卡在哪一环：手机没拍到？拍到了没送到？还是送到了模型没看？

现在直播条上有一枚小灯，4 秒刷新一次，直接读服务端的 `lastPushAt`：

- 绿：**电脑已收到 · N 秒前** —— 帧真的到了，问题在后半段（点评那句话）。
- 橙：**电脑还没收到** —— 帧压根没送出手机，看设置里的自检 / 直传。

不用打开任何面板，也不用问我，抬眼就能判断。

### 15.44 顺序改成「浏览器流优先」，而且失败原因不再被覆盖（1.5.24）

**顺序统一**：三条路一律按 `浏览器流 → 原生逐帧 → 原生取景层` 依次尝试。

- 浏览器流不经过原生桥，也不在页面上叠任何原生 View —— 既最不容易静默失败，也绝不会盖住会话；
- App 从 https 入口打开时同样走这条（WebView 有相机权限就能拿到画面）；
- 原生取景层退到最后，只有前两条都不行才用。

**原因不再被覆盖**：原来的问题是——第一条路的失败原因（比如「镜头被别的应用占着」）
会给后面几条路的笼统失败语盖掉，最后只剩「换成直传也没成」这种话。现在每一场直播会记住
**第一条具体原因**（`firstWhy`），换路时写在状态行里，全灭时的结论也用它。

想手动指定先走哪条（排障用）：`localStorage['dsh.liveSrc'] = 'native' | 'poll' | 'browser'`。

### 15.45 自检不再「0/0 说不知道」，也不再挂死（1.5.25）

早先 `tests/e2e.mjs` 是界面回归，界面这几个月换过几轮，它已经跟不上了；更糟的是它卡在某一步时
会一直等下去，最后被外面 90 秒砍掉，日志只剩一行 `0/0 未通过（中途中断）` —— 看不出任何原因。

现在：

- `tests/e2e.mjs` 有**整体硬超时**（默认 75 秒，`PHONE_E2E_TIMEOUT_MS` 可改），到点会打印
  `FAIL 回归整体超时（N 秒，卡在：<那一步的名字>）`，并补一行汇总，不再靠外面砍。
- `runE2E()` 认得两种汇总格式（老 `== N/M 通过 ==` 与 camtest 的 `通过 N 项，失败 M 项`），
  并把**第一条失败**带进结果与日志。
- 想用摄像头那条线的完整回归当自检：`PHONE_E2E_SCRIPT=test/camtest.mjs`（约 3 分钟）。

### 15.46 诊断面板最上面三行，就是「为什么没截到帧」的答案（1.5.26）

设置里那颗「全链路诊断」现在不只报服务、内存、通道，最上面先回答摄像头这条线：

| 行 | 回答什么 |
| --- | --- |
| 摄像头 · 直播 | 现在开着没有、多久看一眼 |
| 摄像头 · 帧到电脑 | **最后一帧是几秒前到的**，共收到几帧；15 秒内会写「正常：这一帧确实到了电脑」，超了就写「不正常：手机那边没把画面送出来」 |
| 摄像头 · 自检 | 三条路各自 ✓/✗ 与耗时，外加 安全上下文 / 权限 / 原生桥版本 |

一眼就能分清是「手机没拍到」「拍到了没送到」还是「送到了点评那句话出问题」，不用再靠猜。

### 15.47 每帧的「走哪条路 + 花多久」都记着（1.5.27）

推帧时页面会带上两个参数：`via=<来源>` 和 `shotAt=<拍摄时刻的毫秒时间戳>`。
服务端在 `/api/camera/push` 里算出 `ms = 落盘时刻 - shotAt`，把最近 8 帧留在 `cam.recent`：

```js
{ n, at, kb, w, h, via: '浏览器流' | '原生逐帧' | '原生取景' | '未知', ms }
```

诊断面板顶部因此多三行「摄像头 · 帧 最新 / 前 1 眼 / 前 2 眼」：

```
摄像头 · 帧 前 1 眼   960×720 · 8KB · 1303ms
                     原生逐帧 · 25 秒前
```

- `ms` 只在页面确实报了 `shotAt` 时才有值，不编数字；报不出来就只显示尺寸和大小。
- 一位数的毫秒说明手机→电脑这条路很短；上千毫秒说明那一帧在手机端就慢（解码/编码/网络）。

### 15.48 一眼出错也说出来：beat 外面包了一层保险（1.5.28）

以前 `beat()` 里「抓帧 → 补缓冲 → 上传 → 叫点评」这几步，只要中间有一步抛错（上传超时、blob 解码失败、
取景层被系统回收），异常会被 `schedule()` 的 try/catch 吞掉：界面上什么都没发生，看起来就像「这一眼没截到帧」。

现在外面多了一层 `beatSafe()`：

- 出错时状态行写「这一眼内部出错（原因），我换条路再试」；
- 同一原因进设置面板的帧日志（`✗ … 内部错误：…`）；
- 顺手换下一条抓帧路，不在一根坏管子上继续撞。

另外补帧（`pushBuffer`）与原生直传现在都会带 `via`，诊断面板里每一帧都能看出是
`浏览器流 / 原生逐帧 / 原生取景 / 原生直传` 里的哪一条。

### 15.49 大图塞不进内联上限时，先压一张小图（1.5.29）

内联兜底（上传失败时把画面塞进点评请求）原来只管 1.6MB 以内的帧。
如果画质设到 2560 宽 / 98%，一张帧常常 2–3MB —— 上传再一失败，就变成「这一帧哪儿都没去」，模型只能说没取到画面。

现在多了一步：

1. 帧超过 1.6MB 且上传失败 → `recode(blob, 1280, 0.7)` 压一张小图；
2. 小图进内联请求，状态行标「**发的是一张小图**」；
3. 压不动或仍超限，才真的放弃（并留下原因）。

回归里加了一条：内联那一帧的 base64 换回 KB 必须 ≤ 1600，超了就判失败。

### 15.50 只要预览还在画，就先从预览里取帧（APK 1.9.2）

`liveGrab()` 原来的顺序是：

```java
if (liveGrabbing) { camSay("直播那一帧还没回来"); return true; }   // ← 声称处理了
if (grabFromView(liveView, 1280)) return true;
```

`liveGrabbing` 是静帧那条路的闸门，要等 2.5 秒看门狗才放开。闸门关着的时候这个方法返回 `true`，
但**一帧都没交出去** —— 页面就只能等到 6 秒超时，说「没截取到帧」。

现在把取预览提到最前面：

```java
if (!liveOn) return false;
if (liveView != null && grabFromView(liveView, 1280)) return true;  // 屏幕上有画面就一定拿得到
if (liveGrabbing) { camSay("直播那一帧还没回来"); return true; }
```

两条路互不干扰（预览走 `getBitmap`、静帧走 `ImageReader`），所以先试预览没有任何代价。
APK 版本 1.9.2，dex 59,404 字节。

### 15.51 空白帧不再冒充「有帧」（APK 1.9.3）

预览还没出画的时候，`TextureView.getBitmap()` 不会返回 null，而是给一张**纯色位图**。
以前这张图会被当成正常帧交出去：电脑确实收到了、面板上「电脑已收到」还是绿的，
可模型看到的就是一片黑 —— 于是它说「什么都没有」，而你在手机上看到的是「明明拍了」。

新增 `isBlankBitmap(Bitmap)`：抽 24×24 个点比较颜色，**≥99% 同色**就判为空白，
直接 `recycle()` 掉并返回 `false`，让调用方退到 `ImageReader` 那条真正的静帧路。

- 顺带的状态行提示：「预览还没出画，改用静帧」。
- 白墙 / 纯色桌面这类**真实**的纯色场景也会被误判一次，代价只是多走一次静帧：
  静帧拿到的还是同一幅画面，不会丢帧。
- APK 1.9.3，dex 59,800 字节。

### 15.52 窄屏下直播条不再挤成一团（1.5.30）

小屏（320–390 宽）上，直播条标题行原来会把「⚙ / 停止」挤到右边外面去。现在：

- 标题行允许换行，状态文字 `flex:1 1 110px` 会被截断成「…」而不是把按钮顶出去；
- 「电脑已收到」小灯用 `order:9` 自动落到第二行，单独占一行，不跟按钮抢位置；
- 下面一行（间隔下拉 + 现在就看）同样允许换行，「现在就看」始终贴右。

320×700 实测：标题行 = 绿点 + 直播 + 灰状态（截断）+ ⚙ + 停止，小灯独占第二行，画面 3:4 完整可见。

### 15.53 请求自己带着画面时，不再被「没有新帧」挡回去（1.5.31）

这是「没截取到帧」最后一个藏得比较深的坑。

`/api/live/comment` 原来第一件事是查缓冲：最近一帧超过 7 秒就 409 `no-frame`，理由是「别让模型对着旧帧编」。
但手机其实一直有两条送帧的路：`push`（往缓冲里塞）和 `upload`（随点评请求带一张附件）。
**push 那条断了、upload 却成功**的时候，缓冲是旧的 → 直接 409 → 那张明明拍到了的照片哪儿都没去，
用户看到的就是「没截取到帧」。

现在判定改成：这一条请求自己带着画面（`path` 或内联 `data`）就不算「没有新画面」；
只有「缓冲旧 + 请求也没带图」才 409。顺带在日志里写清楚是靠缓冲还是靠请求带来的那张。

回归脚本：`node test/carries-check.mjs`（等 9 秒让缓冲过期 → 只带 data 发点评 → 期望 200）。

### 15.54 这一帧直接作为「图片块」递给模型（1.5.32）

这是「没截取到帧」最根本的一处：**图从来没真正进过模型的上下文。**

原来手机这一眼走到最后是 `enqueue(text, files, …)`，而 `files` 到了模型那边只是注释里的一行**路径**：

```
[附件] 手机发来 1 个文件，已经存到本机：
- D:\…\uploads\live-2026….jpg（live-….jpg，8 KB，image/jpeg）
```

模型只有**自己主动去读那个文件**才看得见画面。它没读（或者没意识到要读），就只能回答「没取到画面」——
而主人看到的就是「没截取到帧」。

现在 `runner-sdk.mjs` 的 `session/prompt` 会把这一帧作为 ACP 的 **image content block** 一起发过去：

```js
{ type: 'image', data: '<base64>', mimeType: 'image/jpeg' }
```

- 只有 `/api/live/comment` 这一条会带图（其它消息不受影响）；
- 每轮最多两张，单张 ≤ 1.2 MB（超过就退回「只给路径」并记日志）；
- 合并队列时，只要其中一条带着画面，图也跟着这一轮过去。

验证：`node test/imgblock-check.mjs`（把 `test/out/probe-shot.jpg` 当这一眼发出去，等模型回话）。
实测回复：「画面只有一片蓝底，中间写着白字「phone-eye」，看着是测试占位图」——**没让它读文件，它自己看见了。**

### 15.55 停播后留一条小结（1.5.33）

直播停下来的时候，会话里会多一行灰字：

> ［直播结束 · 看了 12 眼 · 约 4 分钟 · 大致 96 KB］

- 由页面在 `stop()` 里报数（眼数 × 单帧大小估算流量），服务端 `POST /api/camera/live/note` 的
  `{state:'ended', eyes, minutes, kb}` 分支写成一条系统注记；
- **不进模型、不花一次调用**；
- 数据都在服务端夹过范围（眼数 ≤9999、分钟 ≤1440、KB ≤999999），页面乱报也写不出荒唐数字。

这样一场直播结束后，回头能看到「这一场到底看了多少、花了多少流量」。

### 15.58 他到底看到了什么，画面上有凭据（1.5.36）

「有没有截到帧」这件事不该靠读日志。每一眼真的发出去之后，画面右上角会出现一张 54×54 的
缩略图，角上写着「已送出」——那就是**电脑收到的、模型看到的**那一张。

- 点缩略图 → 站内大图（和会话里的照片同一个查看器）；
- 停播时缩略图自动收掉，不留上一次的旧画面误导人；

### 15.59 直播时屏幕不黑（1.5.37 + APK 1.9.4）

直播最怕的不是网络，是**屏幕自己熄掉**：一熄屏，WebView 就被系统挂起，JS 停摆、
那一整段等于白看，回来只剩一句「手机把页面切到后台了」。

- APK 侧：`MainActivity` 新增 `keepScreenOn(boolean)`，`liveOn = true` 时
  `getWindow().addFlags(FLAG_KEEP_SCREEN_ON)`，`stopLive()` 里立刻 `clearFlags`
  —— 只有直播期间常亮，退出直播绝不常驻。
- 页面侧：直播设置里多一行说明「开直播这段时间屏幕会一直亮着」。
- APK 版本 **1.9.4**（45,855 B），dex 里能查到 `1.9.4` 与 `keepScreenOn`。
  （`FLAG_KEEP_SCREEN_ON` 是 `static final int`，会被 javac 内联成字面量，
  所以 dex 里查不到这个字段名，属正常。）

### 15.60 手机丢一帧，不再把整场直播掐掉（1.5.38）

以前只要有一眼没拍到，就会立刻换路；三条路换完就判「都不行」，直接把直播停掉。手机上偶尔丢一帧很常见——镜头被别的应用抢一下、锁屏前那一瞬间、切后台——结果主人看到的就是「直播自己停了」。

现在的规矩：

- **一眼没拍成不算失败**：只记一笔，状态行写清原因，接着按原来的间隔再来一次。
- **连着两回没拍成才换路**：一帧抖动不会把三条路一口气走完。
- **三条路都连着失败，也不停播**：改成每 20 秒慢慢试一轮，状态行写「我会每 20 秒再试一次，修好就自动接着看」。相机一恢复，下一轮就自己接着看。
- **第一眼没拍成，先把处置卡片摆出来**：写明是权限、还是 https、还是镜头被占着，能点的按钮都在卡片上（重试 / 拍一张 / 收起）。卡片只是提示，不影响后台继续重试。
- **服务端把最短间隔从 3 秒放到 1.5 秒**：设置里选「2 秒」这一档才真的按 2 秒走，不会隔一轮就被 429 挡回来。

自测：`node test/live-stress.mjs`（相机 45% 概率丢帧，10 秒一眼跑 45 秒，再修好观察 30 秒）——9 项全过：全程在跑、失败都记账、没卡在取帧、修好后自己接着看、停得干净、0 个 JS 错误。界面回归 79 项全过。

### 15.61 角标说实话：先「已送到」，他答上话了才「他看到了（1.5.39）」

画面右上角那张缩略图原来一直写「已送出」——可「送出」只是说这一帧离开手机了，不代表他真看到。现在分两步：

- 一眼拍成、发出去：角标写 **「已送到」**（绿色细边）。
- 这一帧发出去之后真的来了回复：角标换成 **「他看到了」**，边框转绿。
- 两分钟以前的旧帧不会被标成「他看到了」——不然人会以为他一直在看一张早就过期的画面。

实现上没加任何请求：页面本来就在收 SSE，回复落地那一处顺手喊一声 `window.__markSeenViewed()`（跨作用域，必须走 window）。界面回归 82 项全过。

### 15.62 切后台只暂停，回来接着看（1.5.40）

以前页面一被藏起来（切到别的应用、锁屏、按返回）就直接 `stop()`：镜头和取景层是收掉了，可整场直播也跟着结束了——回来还得手动再点一次开播，会话里还多一条「直播结束」小结。

现在分开两头：

- **看不见了 = 暂停**：清掉定时器、收掉取景层（`closeOverlay()` + `setPreviewVisible(false)`）、告诉服务端「先不看」，状态行写「页面在后台，先不看（回来我接着看）」。`running` 保持为真。
- **回来了 = 接着看**：状态行「回来了，接着看」，立刻排下一眼。离开超过 10 分钟就当这一场结束，改成收摊（省电，也不留着一条早就没用的会话）。
- **真离开页面**（`pagehide`，URL 变了 / 页面关掉）才 `stop()` 收摊。

回归新增 `[16]` 六项（暂停还活着 / 状态行说明 / 取景层收掉 / 回来还在看 / 回来能接着取帧 / 状态行反馈）→ 89/89。

### 15.63 手机端条款跟桌面同一份 + 会话失效自愈（1.5.41）

**条款**：手机 profile 的 `local-prompt-inject` 以前指向 `phone-bridge/phone-inject.md` —— 那是 2026-11-01 写的 1.4 KB 精简版，桌面上 31 KB 的总条款有一大半没传到手机。

现在服务端启动时读 `DSH_HOME/prompt-inject.md`（可用 `PHONE_PROMPT_INJECT` 覆盖），去掉聊天模板标记行（`<|im_start|>` / `<|im_end|>` / `<project_instructions>`）后写到 `runtime/inject-phone.md`，手机 profile 指这份清理副本：**正文一字不改，只去掉标记**。

> 血的教训：一开始图省事直接指桌面那份原文件，手机每条消息都 `exit=1 text=0`、一个字不回——`<|im_start|>system:` 这种标记被原样拼进 system 段发给接口，接口直接报错。模板标记必须在注入前吃掉。

实测：问「你该怎么称呼我？」→「咕噜咕噜……主人，本鲸叫你**主人**呀，这一句就够了～」，条款确实到了手机。

**会话失效自愈**：会话文件被清掉/换过 `DSH_HOME` 之后，DSH 只会 exit=1 并在 stderr 说一句 `session "…" does not exist; omit --session-id to start a new Session`，手机那头一片空白。现在两道保险：

1. 开跑前先确认会话还在（`listSessions()`），不在就当场换新会话；
2. 万一下去才发现（错误文本里带 `does not exist`），丢掉坏会话、把这条消息用新会话**自动重跑一次**（只重来一次，防打转），主人不用重发、也不用点任何东西。

**APK 版本误报**：以前只凭 `DSHCam.version` 取不到就弹「手机上的 App 还是旧版」，个别 WebView/旧壳取不到就会被冤枉。现在只要新接口（`setUpload` / `liveOn`）在，就照常走原生那条路，只在状态行留一句「App 没报版本号」。

### 15.64 「打开摄像头失败」不再让人自己猜（1.5.42 + APK 1.9.5）

真机日志把这件事说清楚了：

```
camera 自检 失败 · 都失败 · 浏览器：NotAllowedError
camera 自检分路：浏览器✗ 81ms(NotAllowedError) · 原生✗ 6004ms(正在打开摄像头…)
camera 自检环境 · 安全上下文=是 · 权限=prompt · 原生桥=在
```

两条路一起断：浏览器那条 81 毫秒就被拒（说明 WebView 直接回了 NotAllowedError，根本没弹系统权限框），原生那条等了 6 秒没画面（Camera2 没拿到相机）。根子是同一件事——**相机权限没到手**。

以前页面只会等超时，然后飘一句「打开摄像头失败」，人不知道该点哪儿：拒绝过一次之后浏览器**不会**再弹窗，点一百次「再试一次」都是同样的失败。现在改成三件事：

1. **先查权限再动手**：`beatInner()` 第一眼前先问一次状态（App 里走 `DSHCam.permState()`，浏览器里走 `navigator.permissions.query({name:"camera"})`）。已经是 `denied` 就当场把卡片摆出来，不再白等十几秒。
2. **卡片给能点的按钮**：在 APK 里按钮是「打开系统设置」——新加的 `DSHCam.openSettings()` 直接跳到本应用的权限页（`ACTION_APPLICATION_DETAILS_SETTINGS`）；浏览器里按钮是「再问一次权限」，同时正文写清「拒绝过就不会再弹，得去地址栏小锁里改」。
3. **还留一条后路**：卡片上的「拍一张给他看」永远在——直播这条路一时通不了，用系统相机拍一张照样能发进会话。

APK 侧新增两个接口：`permState()` 回 `granted` / `denied` / `prompt`，`openSettings()` 跳权限页。版本 1.9.5，dex 里能查到 `permState`、`openSettings`、`1.9.5`。

实测（假桥把 `permState()` 固定成 `denied`）：卡片标题「相机权限被挡了」、按钮「打开系统设置」、点一下 `openSettings` 调用计数 1，截图 `test/out/20-perm-card.png`。

### 15.65 全黑帧不再当「拍到了」

相机没授权、或者被别的应用占着的时候，`getUserMedia` 有时照样给一条流，
但流里一帧都没有 —— canvas 画出来是纯黑，以前照样压缩上传，
电脑收到一片黑，模型只能回「看不出来」。现在这条被拦住了：

- 取帧前先看轨道：`track.muted` 或 `readyState === "ended"` 就直接判失败，
  状态行写「相机的流没在出画面（权限被收走了，或者相机被别的应用占着）」。
- 画完再抽样判一次：缩到 32×32，算平均亮度和方差，`mean < 8 && var < 25` 判全黑。
  全黑不发、不算一次「拍到」，卡片会摆出「打开系统设置」（App 里）或
  「再问一次权限」（浏览器里）。
- 深色但正常的画面不会被误判（`#101010` 与有内容的画面都判为「不空」）。

这样「电脑上看到一片黑」从此只有一种解释：权限没给，页面会直接告诉你。

### 15.66 公网连不上：远端端口被上次的隧道占着

今天公网 `https://<你的域名>/dsh` 打不开，服务器上却是好的 —— 
`ss -ltnp` 显示 `127.0.0.1:18899` 被一个 sshd 占着，那个连接全是 `CLOSE-WAIT`：
客户端（我这边的 ssh）早就没了，远端还挂着监听，于是新的隧道报
`remote port forwarding failed for listen port 18899`，一直重建失败。

`link.mjs` 现在这么处理（`selfhost` 后端）：

- 起隧道**之前**先跑一次 `freeRemotePort()`：在服务器上查这个端口是谁在听，
  **只杀进程名以 `sshd` 开头的**（`ps -p PID -o comm=` 判断）；
  端口上蹲着别的东西就跳过、打印 `skip:<pid>:<name>`，绝不乱杀。
- 连完探活 30 秒；失败时把 `remote port forwarding failed` 翻译成人话
  「服务器上远端端口 N 被占着（上一次的隧道没断干净），已经试着清掉它」，
  然后**清一次再试一遍**，两遍都不成才报错。

验证：故意在服务器上用 `/tmp/sshd`（名字就叫 sshd 的 nc）占住 18899，
再点开隧道 —— 占位进程被清掉，新隧道绑定成功，
公网 `api/health` 与本地 `uiVersion` 完全一致（同一个桥接）。
### 15.67 原生那条路也要拦全黑帧（1.5.45 + APK 1.9.6）

手机上点开直播，电脑确实收到了帧（1280×720、6KB），但整张是黑的——
而且自检还写着「原生 ✓ 拿到了帧」。

查下来：亮度的检查只加在**预览那条路**（TextureView 截图），
Camera2 的 `ImageReader` 静帧走的是另一个函数 `jpegToB64`，
它只解码和缩放，纯黑的 JPEG 照样编码、照样上传、照样算「拍到了」。
所以「收到了，但一片黑」。

改了两处：

- **APK**：`jpegToB64` 解码后先判空白（抽 24×24 点，99% 同色就算空白），
  空白就把这一帧丢掉并回一句「预览没出画（画面全黑），这一帧不算」；
  两条静帧回调的失败文案改成「相机没出画（画面全黑）」。
- **页面**：不管这一帧来自哪条路，发出去之前都再量一次亮度
  （`isBlankBlob`，32×32 抽样），全黑就按失败处理——
  这样以后任何新加的取帧路径都自动被这一关兜住。

配套：全黑时弹出的卡片换成「相机开了，但画面全黑」，
正文直接写清荣耀/华为还要看「隐私 → 相机」总开关，
并给出一条最稳的退路「用系统相机拍一张」。

验证：假桥喂纯黑 JPEG → 状态行「画面全黑：相机没出画（blank）」、
这一帧没上传、失败计数 +1、卡片弹出（`lbcoach show`），
回归 89/89。
### 15.68 「全黑」这件事现在有账可查（1.5.46）

以前「画面怎么是黑的」只能靠人说一遍，日志里只有「收到帧 6KB」。
现在手机上量出这一帧是黑的，会顺手报给电脑一声：

- 手机：`tellBlank()` 打一下 `POST /api/camera/blank`，带上原因；
  失败也不影响取帧（发完就忘）。
- 电脑：`cam.blank = { n, at, why }` 记账，前三次和每 20 次写一行日志
  「拦下全黑帧 #N（这一帧没发出去）」。
- 诊断面板：从 `/api/diag` 的 `camera.blank` 读，多一行
  「摄像头 · 全黑帧」——「没有」/「拦下 N 张 + 最近一次多久以前」，
  并直接给下一步（权限 → 隐私开关 → 被别的应用占着）。

顺手修的两处：

- 那一行原来被塞在「自检」的 if 分支里，没跑过自检就看不到 → 挪到分支外；
- 诊断面板里 `ago()` 收的是**秒**，我先给了毫秒（会显示成几十万小时）→ 先除 1000。

验证：回归新增 `[17]` 三项（记账、诊断接口带数、页面挂出上报入口），92/92。
### 15.69 自检给一句话的结论（1.5.47）

手机上的「测一下现在的画面」以前只把三条路的结果摆出来（`浏览器 ✗ NotAllowedError · 原生 ✓ 800ms`）。
懂行的人看得懂，不懂的人还是不知道该点哪儿 —— 主人报「打开摄像头失败」「还是全黑」时，屏幕上就是这几行。

现在按下之后，面板上多一张卡片：一句话说清现在是什么状况，加一个**能点的**按钮。

| 状况 | 卡片标题 | 按钮 |
| --- | --- | --- |
| 有一条路通了，而且这一帧真有画面 | 相机正常，画面能出来（附尺寸 / 大小） | 无 |
| 相机能开，但这一帧全黑 | 相机能开，但这一帧是黑的 | 用系统相机拍一张 |
| 权限被挡 / 浏览器 NotAllowedError | 相机权限被挡了 | 打开系统设置 |
| 不是 https，浏览器根本不给摄像头 | 这个地址打不开摄像头 | 用 https 那个地址打开 |
| App 太旧（cam2/1.8 及以前） | 手机上的 App 有点旧 | 装一下新包 |
| 以上都不是 | 相机这条路现在走不通（带原因） | 再试一次 |

顺序有意义：**「能出画」优先**。浏览器那条路在桌面、无头、旧 WebView 里几乎总是 `NotAllowedError`，
如果按「有错就报错」的顺序，一条原生路明明通了也会被判成权限问题 —— 这个坑本轮踩过一次。

结论同时在 `/api/camera/probe` 里带 `verdict`，诊断面板多一行「摄像头 · 结论」，
不打开设置也能从诊断面板看到同一句话。

测试：`[18]` 六项（纯函数四种输入各一句、真点一次卡片要出现、按钮存在），回归 99 项全过。

### 15.70 拼正文出错也要回一句话（1.5.48）

每一轮发给模型的正文是 `taskBody(text)` 拼出来的：它要把记忆片段、注入条款（必要时）、工作目录拼在一起。
从前这里是裸调用 —— `child.stdin.write(taskBody(text))`。只要它抛异常（注入文件读不到、记忆文件坏了一行），
这一轮就没人收尾：进程没起、`busy` 一直是 `true`，手机停在「他还在想…」，一个字都不回。
日志里只留一行 `warn unhandledRejection ReferenceError: …`，主人那边则是一片空白。

现在正文在**起进程之前**先拼好，拼失败就当场回一句话：

```text
这一轮我这边内部出错了（<原因>），没能开始想。再发一次试试；一直这样就把这条消息截图给我看。
```

同时把这一轮正常收尾：`appendMessage` 落盘、`turn_end` 广播、`busy = false`、`schedulePump()`，
下一条消息照常排队，不会卡死整条通道。

> 一句话：**宁可让主人看到「我出错了」，也别让他看着空气猜。**

### 15.71 手指点得着的按钮（1.5.49）

手机上最大的抱怨从来不是「不好看」，是「点了没反应」—— 有时候是真的没反应，
有时候是**按钮只有 25 像素高，拇指压不准**。这轮把所有可点元素量了一遍：

| 元素 | 原来 | 现在 |
| --- | --- | --- |
| 任务 / 相处 切换 `.modebar button` | 31px | 38px |
| 快捷回复小胶囊 `.quick button` | 30px（`padding:6px 12px`） | 36px（`padding:9px 14px`） |
| 出错卡片的「展开详情 / 复制错误 / 重发这句」 | 25px（`padding:4px 9px`） | 36px（`padding:8px 11px`） |

量法：无头浏览器 390×844@2x 下遍历 `button, .btn2, .qbtn, .fb, .mic, .send, .fscope, .sitem, .vopt, .mopt, .camicon`，
取 `getBoundingClientRect()`，宽或高小于 34px 的就列出来。现在这个列表是空的。

同时确认页面自检 `window.__uiFails` 与 `window.__deadBtns` 都是空的 —— 没有看着在、点了没反应的按钮。

### 15.72 浅色主题：白底上的白字（1.5.50）

**问题**：手机切到浅色主题后，直播设置面板与结论卡几乎整片看不见 —— 标题「直播设置」、
「压缩质量」、结论卡「相机权限被挡了」全是 `#fff` / `#e9f1f9` 这类给深色底写的颜色，
压在白色面板上等于白底白字。直播条本身也还是那块深色取景带，在浅色页面里像贴了块黑胶布。

**改法**（`public/app.html`，全部走 `body.light` 覆盖，深色主题一个像素没动）：

- 面板文字：`.camtitle` / `.cfglab b` / `.cfglab span` / `.cfghint` / `.cfgest` 换成深蓝灰；
- 控件：`.cfgchip`、`.cfgtest`、`.camicon`、`.cfglog` 换成白底 + 浅边 + 深字；
- 结论卡：`.verdict` 三档底色改成低透明度、`.verdict b` 用 `#12233a`、`.vbtn` 换成浅蓝按钮；
- 直播条：`.livebar` 外壳换成浅灰渐变，`.lbtitle` / `.lbmsg` / `.lbbtn` / `.lbgear` / `.lbask` /
  `.lbfeed` / `.lbempty` 全部跟着主题走；**预览框继续是黑的**（那是画面本身）。

**怎么确认**：回归新增 `[19]` 两项 —— 切成浅色后真点一次「测一下现在的画面」，
算结论卡标题与卡片底色的 WCAG 对比度（要求 ≥ 4.5:1，现在 13.92:1），并检查面板标题
是不是深色字。截图 `test/out/26-light-verdict.png`、`27-light-coach.png`。

**教训**：颜色写死在一个主题上，早晚会在另一个主题上还债。新加控件时顺手问一句
「白底还看得见吗」，比事后再来一轮对比度审计便宜得多。

### 15.73 浅色主题的小字全部压到 5:1 以上（1.5.51）

**做法**：不再凭眼睛挑，写了个扫描器 `test/contrast-audit.mjs` —— 在浅色主题下把主会话、
设置、直播设置、诊断四个界面里每个「自带文字」的元素跟它的实际底色（半透明层层叠到白纸上）
算 WCAG 对比度，低于 4.5:1（大字号 3:1）就列出来。第一次跑，主会话 40 处、设置 40 处。

**扫出来的真问题**：

- `.vnote .vt` 3.42:1（语音标签）、`.mmeta` 3.29:1（耗时那行）、`.shotcap` 2.95:1（照片说明）——
  手机上歪个头就糊；
- 设置面板的一堆说明字是**写在标签 `style=""` 里的**（`#7d8ea6` 是深色主题的值），
  样式表管不到，只能 `body.light .kv{color:#56687c !important}` 压一次；
- `#cfg-info b`、`.kv b` 由 id 选择器定色，优先级高于类选择器，得单独写；
- 时间分隔条 `.daysep span` 在浅色里还是「深色药丸」，换成浅底；
- 主按钮 `.btn2.pri` 原来是白字配浅青渐变（青那头只有 2.3:1），渐变改深（`#12876c → #2f57c9`）。

**扫描器的盲区也写进脚本了**：渐变底算不出「那一个颜色」、emoji 根本不吃 `color`，
这两类直接跳过并在报告里报数（现在各界面跳过 7–12 个），免得天天报假红。
注意渐变只能看**元素自己和上一层**，一路往上找会被整页背景的渐变全部命中、全部跳过。

**结果**：四个界面浅色主题下 0 处低于 4.5:1；深色主题一个像素没动；回归 101/101。
